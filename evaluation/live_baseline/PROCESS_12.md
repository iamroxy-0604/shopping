# 12 条需求配对试运行：实验过程记录

## 运行前

1. 将用户审阅后的 12 条充电宝需求写入 `scenarios_v2.json`。每条保存公开初始需求、隐藏的必须条件、可权衡偏好、B 组属性反馈顺序。
2. 规定每条分别运行 A、B，首批共享同一次淘宝实时搜索结果；每批展示 3 件，最多 5 批；不由脚本主动提问。
3. 当前淘宝联盟接口返回商品标题、接口价格等字段，不能可靠核查重量、USB-C 实际输出、双设备同时输出、认证详情与兼容性。因此本轮预设的自动判定只是“标题与价格候选匹配”，所有候选均需人工核查，**不记为确认满意**。12 条材料“至少存在一件真实满足条件的商品”尚未全部得到验证。

## 实际执行

在仓库根目录使用本机 `backend/.env` 中已配置的淘宝联盟权限，运行：

```powershell
node --env-file=backend/.env evaluation/live_baseline/run_v2.mjs
```

最终有效运行目录：`runs/2026-11-06T07-40-53-367Z/`。运行时对每条需求先取共享首批；A 组始终只反馈“不满意”，随后按原搜索结果继续取商品；B 组每次未出现候选后，按预设顺序补充一项必须条件并重新检索。过窄查询无法凑齐 3 件时，脚本按已公开的初始词、最后一项属性词及“充电宝”回退检索，并在日志中保存每次实际查询。脚本用 ID 与规范化标题排除同组已展示商品。

日志顺序为：`experiment_start` → 对每条需求的 `scenario_start` → `search_request/search_response` → `group_start` → 每批 `batch_judged` 与可能的 `user_feedback` → `group_end/scenario_end`。`events.jsonl` 保留淘宝返回的候选池、实际展示的三件、逐条件证据状态和停止原因；`summary.json` 保存 24 次交互的逐批结构化结果。淘宝推广链接含跟踪参数，未写入公开日志；密钥只留在本机 `.env`。

执行完成后运行：

```powershell
node evaluation/live_baseline/validate_v2.mjs evaluation/live_baseline/runs/2026-11-06T07-40-53-367Z
node evaluation/live_baseline/make_review_queue.mjs evaluation/live_baseline/runs/2026-11-06T07-40-53-367Z
```

校验覆盖 12 个 A/B 配对、两组首批一致、每批恰好 3 件、每组不重复标题、最多 5 批、逐项判定与停止结果一致。人工复核表为 `review_queue.csv`，11 行候选的 `decision` 均保持“待核查”。

## 本轮状态

24 次交互全部完成；383 条事件、77 次实时淘宝请求，接口错误 0 次，少于 3 件的展示批次 0 次。A 组共展示 47 批，B 组 43 批并补充 19 次属性。A 组 5 条、B 组 6 条出现标题与价格候选；**确认满意数目前均为 0，原因是尚未完成商品详情人工复核**。未出现候选的需求也尚不能判定为“商品库不存在合格商品”或“推荐失败”。
