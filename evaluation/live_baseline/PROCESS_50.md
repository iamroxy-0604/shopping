# 50 条需求配对实验过程

## 材料固定

用 `generate_50.mjs` 生成 10 种使用情境、每种 5 条，共 50 条不同初始需求。每条在运行前固定容量、功能或规格、价格三项隐藏必须条件及 B 组的容量→功能或规格→预算反馈顺序。`CARDS_50.md` 是人可读清单；`scenarios_50.json` 是机器可读材料；运行目录内 `scenarios_snapshot.json` 保存实际使用的原始副本。

这些是人为构造的便利样本，不是随机抽取的真实用户请求。商品库可行性和详情证据尚未逐条核验，因此本轮目标为扩展流程与检索试运行。

## A/B 执行规则

1. 每条材料先以公开初始需求检索淘宝。若首批不足 3 件，先由共享检索补齐；A、B 获得完全相同的 3 件首批商品。
2. 每批恰好展示 3 件，最多 5 批。A 组在没有标题与价格候选时只反馈“不满意”，不提供隐藏条件；B 组按预定顺序每轮补充一个条件。
3. 搜索词过窄时依次回退到公开初始词或通用“充电宝”词；回退请求也写入日志。同组按商品 ID 和规范化标题去重，同批内部也去重。
4. 脚本检查淘宝接口价格和卖家标题。全部符合预设规则时记为“待核查候选”并停止该组；这不是确认满意。若 5 批内未检出，记为“未检出候选”，不推断该商品不存在。
5. 两组均由实验脚本模拟用户反馈，没有真实用户购买决策，也没有运行会主动问卷的 Wit 智能体。

## 运行与核验

在仓库根目录执行：

```powershell
node evaluation/live_baseline/generate_50.mjs
node --env-file=backend/.env evaluation/live_baseline/run_v2.mjs evaluation/live_baseline/scenarios_50.json
node evaluation/live_baseline/validate_v2.mjs evaluation/live_baseline/runs/2026-11-06T08-34-32-644Z
node evaluation/live_baseline/make_review_queue.mjs evaluation/live_baseline/runs/2026-11-06T08-34-32-644Z
node evaluation/live_baseline/make_report_50.mjs evaluation/live_baseline/runs/2026-11-06T08-34-32-644Z
```

最终有效运行目录为 `runs/2026-11-06T08-34-32-644Z/`。校验通过：50 个配对、100 次交互；同一材料的 A/B 首批一致；所有实际展示批次各 3 件；同组无重复标题；每组不超过 5 批。实时淘宝搜索请求 414 次，无接口错误。原始日志有 1945 条事件。

运行前曾有两次未通过完整校验的本地调试试跑：一次暴露同批内重复标题，一次暴露少数材料在补齐首批时 A/B 结果不一致。修复后重新完整运行，并只以本目录为有效结果。调试试跑不进入正式报告或 GitHub 提交。

## 日志结构与人工复核

`events.jsonl` 按时间记录实验设置、每条材料、共享首批、A/B 搜索请求和淘宝响应、每批三件商品及每项条件的证据状态、模拟用户反馈、停止原因。`summary.json` 保存全部 50 对的逐批结果。公开日志不包含淘宝密钥、推广链接跟踪参数或用户账号。`review_queue.csv` 包含 21 条候选记录，预留详情证据、审核人和结论字段。

确认商品满意需要核实接口价格所对应的实际规格，以及容量、重量、输出功率、接口、认证和兼容性等条件；标题未写某项规格时也不能直接判不符合。正式研究应先逐条确认至少存在一件合格商品，再让人工或受控模拟用户对每批作一致判定，随后计算真正的 5 批内成功率及批次差异。
