# 链接转接器交接汇总报告

更新日期：2026-10-18  
交接目的：将独立的链接读取与 A2UI 展示模块接入购物智能体，同时保留其通用性。

## 1. 当前状态

- 模块位于 `link-bridge/`，独立运行，不依赖购物智能体的会话、问卷、商品搜索或业务状态。
- 当前实现是可运行的本地原型：用户粘贴一个链接，服务读取真实页面信息，生成统一记录；A2UI 实验页再把记录编排成卡片。
- A2UI 使用官方 `@a2ui/lit` 与 `@a2ui/web_core`，锁定版本 `0.13.0`，输出协议 `v0.9.1`、官方 `basic` 组件目录。
- 展示选择由确定性规则完成，**当前没有 LLM 参与**。
- 自动化测试共 20 项，最近一次 `npm test` 全部通过；前端 Bundle 可由 `npm start` 构建。
- **尚未接入购物智能体整体链路**。现阶段只是独立服务与独立预览页面。

## 3. 当前数据流

```text
演示页或智能体
  └─ POST /api/resolve { url }
       └─ URL 安全校验与平台路由
            ├─ OpenCLI 站点命令
            ├─ OpenCLI Browser Bridge（需要已连接的 Chrome 扩展/登录态）
            └─ 公开网页元信息回退
       └─ 返回统一内容记录 ContentRecord
            ├─ 购物智能体可直接消费记录（当前尚未接入）
            └─ POST /api/compose { record, mode }
                 └─ 返回 A2UI v0.9.1 消息
                      └─ A2UI Lit Renderer 渲染界面
```

读取和呈现是两层：`/api/resolve` 不负责决定购物意图或生成 UI；`/api/compose` 不访问原网站，只使用传入的记录生成展示结构。

## 4. 当前接口

服务默认监听 `127.0.0.1:3100`。

### `GET /health`

健康检查，正常返回 `{ "ok": true, "service": "link-bridge" }`。

### `POST /api/resolve`

请求：

```json
{ "url": "https://www.xiaohongshu.com/explore/..." }
```

成功返回 `{ "ok": true, "record": { ... } }`。当前记录字段包括：

```text
id, source { url, platform }, contentType,
title, body, description, cover, images[], video, embed,
readBy[], status, availability { text, cover, video, embed }, issue
```

- `contentType`：`video`、`image`、`article`、`unknown`。
- `status`：`complete`、`partial`、`unavailable`。`complete` 表示读取到了主要文字内容，不代表图片/视频一定能在每个客户端播放。
- `availability.cover` 表示取得了封面 URL，不等于远端图片已被目标客户端成功加载。
- `video` 是直链视频文件（MP4/WebM）；`embed` 是平台官方播放器入口。两者不可混为一谈。
- `readBy` 记录实际成功的读取路径，如 OpenCLI 站点适配器、Browser Bridge、公开网页回退。
- `issue` 提供机器可读问题标识，例如 `official_embed`、`video_unavailable`、`content_unavailable`、`search_results_page`。

### `POST /api/compose`

请求：

```json
{ "record": { "source": { "url": "https://example.com/post" }, "title": "..." }, "mode": "overview" }
```

`mode` 目前支持 `overview` 和 `detail`。成功返回 `protocol`、`catalogId`、`layout` 和 A2UI `messages[]`。它是当前前端实验接口，尚未升级为计划文档里的 `/v1/compose`，也未实现客户端能力协商。

## 5. 已实现的平台读取与展示行为

- OpenCLI 定向读取：小红书笔记、B 站单条视频、YouTube 视频、微博帖子、知乎问题/回答；字段不足时可继续尝试 Browser Bridge 或网页回退。实际支持以 `src/resolver.mjs` 中的路由为准，不等于 OpenCLI 支持的平台总数。
- Browser Bridge 依赖本机 OpenCLI 与 Chrome 扩展连接；目标站点若需登录，使用对应 Chrome 配置的登录状态。部署到另一台服务或云端时不能假设可访问用户本机 Chrome。
- 小红书搜索结果 URL（`/search_result`、`/search`）会明确提示需要具体笔记链接，不再把搜索页 Logo、页脚等当作笔记内容。
- 小红书图集：优先选取 `sns-webpic*.xhscdn.com` 中的笔记图片，过滤头像与已知平台品牌资源；A2UI 页面设置 `no-referrer`，兼容依赖该请求策略的图片 CDN。
- B 站/YouTube 等视频页面：若只有官方播放器地址而无 MP4/WebM，显示封面、文字与原站入口，不伪装成可直接播放的 A2UI `Video`。
- 首页链接不会被当作单条内容。链接不可读时保留明确状态和原站入口。

## 6. 接入购物智能体的建议流程

1. **先确定触发时机**：购物智能体判断用户发来外部链接、要求解析/参考某条内容时，调用 `POST /api/resolve`。不要把所有聊天消息都发给转接器。
2. **消费统一记录**：将 `record` 作为独立内容来源加入 Agent 上下文，至少保留 `source.url`、`platform`、`contentType`、标题、正文、媒体 URL、`status`、`issue` 和 `readBy`。保留原始出处，标注读取失败或部分可用。
3. **区分内容与商品**：小红书笔记、视频、文章是内容证据，不自动成为 SKU。只有商品页/可信商品数据给出的商品标识、价格、库存等才进入商品实体；笔记提到商品时可作为推荐理由或候选线索，需另外验证商品链接和在售数据。
4. **由购物 Agent 判断下一步**：例如用户“随便逛逛”可把内容卡片列为探索推荐；用户明确购买需求时再进入商品检索/商品卡流程。此意图判断属于购物智能体，不属于当前转接器。
5. **决定 UI 路径**：短期可以继续用购物智能体自己的卡片组件显示 `record`，不必接 A2UI。若目标前端准备验证动态 UI，则把记录和任务交给 `/api/compose`，在同一客户端集成兼容 `v0.9.1 basic` 的 A2UI Renderer。不要把本演示页整个 iframe 嵌进购物流程作为最终集成方案。
6. **保持两层解耦**：推荐链路是“购物 Agent → resolve → 内容记录 → Agent 决策 → 自有 UI 或 compose → Renderer”。建议购物业务先依赖统一记录；A2UI 可作为呈现适配器，失败时回退到购物前端固定卡片。

## 7. 本地运行与验证

在 `link-bridge/` 目录运行：

```powershell
npm install
npm start
npm test
```

- 原预览页：`http://127.0.0.1:3100/`
- A2UI 实验页：`http://127.0.0.1:3100/a2ui.html`
- `npm start` 会先执行 `build:a2ui`，然后启动服务。端口可通过 `PORT` 环境变量调整；当前服务只绑定 loopback。
- A2UI 实验页右侧证据区可查看统一记录和实际传给 Renderer 的消息，便于区分读取错误与 UI 渲染错误。
- 最近一次验证：20 项自动化测试通过；真实小红书笔记重新读取后，统一记录的 `cover` 指向笔记图片，A2UI 页面显示实际笔记图片。

## 8. 当前限制与并入前注意事项

- 现在是本地演示服务，不是面向多个智能体/用户的生产 API：没有鉴权、租户隔离、限流、缓存策略、请求追踪或服务端部署方案。
- API 只监听 `127.0.0.1`，没有 CORS 配置。若购物智能体前端和服务端分端口/分机器，应优先由购物智能体后端代理调用；不要直接暴露当前服务到公网。
- 统一记录是当前原型字段，不是计划中完整的 v2 Schema；缺字段来源证据、媒体逐项加载状态、标准化错误码和批量链接接口。
- `availability.cover` 当前是 URL 是否存在，不做 CDN 可用性验证；签名图片链接可能过期，客户端应处理图片失败并提供文字/原站回退。
- A2UI 只验证了基础 `Card`、`Text`、`Image`、`Video`、`Row`、`Column`、`Button` 的受控示例；没有根据用户任务动态挑选布局，也没有自定义商品组件、任意 HTML 或 LLM 组件生成。
- 内容提取受 OpenCLI 版本、平台网页结构、访问频率、登录状态和签名 URL 有效期影响。真实平台回归需人工抽样；自动化测试主要覆盖模拟返回与服务契约。
- 输入 URL 做了 HTTP/HTTPS、私有地址、DNS、重定向与响应体限制，但接入生产前仍应做安全评审，尤其是服务端代理、超时、缓存和凭证边界。

## 9. 推荐的下一阶段

1. 先选定集成边界：购物后端代理 `/api/resolve`，购物前端消费普通 JSON 记录。
2. 在购物智能体里实现“内容记录”呈现和明确的商品验证步骤，先跑通端到端；A2UI 单独作为可选输出。
3. 冻结稳定的统一记录 Schema、字段来源与媒体可用状态，再把 `/api` 迁移为版本化接口。
4. 用购物智能体的“探索内容”和“明确购买”两种对话分别验收，确认内容推荐和商品推荐不会混为一类。
5. 若多个前端都要动态渲染，再评估 A2UI 版本升级、组件目录白名单和客户端能力协商。

---

**交接结论：** 当前已有可单独运行的链接读取器、统一记录原型、A2UI v0.9.1 演示与基础测试；尚未接入购物智能体的整体链路。集成时优先复用 `/api/resolve` 的记录契约，由购物 Agent 决定它是探索内容还是商品线索，A2UI 只作为可选的 UI 输出层。
