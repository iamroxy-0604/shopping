# 通用多模态链接转接与 A2UI 接入计划

版本：2026-10-16。本文是实施计划，不代表以下功能已经完成。

## 1. 目标与边界

把链接转接器做成可供不同智能体调用的独立服务。调用方输入一个或多个公开链接，服务返回有出处、可核验的内容记录；调用方可以再提供用户任务，由单独的界面编排层生成适合该任务的 A2UI 界面描述。演示网页只是其中一个客户端，不与购物智能体的业务流程绑定。

这里有两项不同的能力：

1. **内容转接**：识别链接、调用 OpenCLI 或其他读取器、统一文字与媒体字段，并说明哪些字段确实可用。
2. **界面编排**：根据记录、用户任务和客户端支持的组件，选择图文、视频、商品、对比或失败提示等展示结构。A2UI 只承载界面结构与交互，不负责抓取网页或理解视频。

第一期以链接详情读取为核心。搜索发现、商品价格与库存、图片识别、视频语音转写都作为可选的上游或后续能力；不能因为链接来自商品站就声称它是可购买的在售 SKU。

## 2. 当前基线

| 已有 | 现状与缺口 |
| --- | --- |
| 独立服务与演示页 | `POST /api/resolve` 接收单个链接，返回一条记录；网页使用固定卡片与弹窗。 |
| OpenCLI | 对小红书、B 站、YouTube、微博、知乎使用站点命令；小红书、通用站点和字段缺失时尝试 Browser Bridge，最后回退公开网页元信息。OpenCLI 支持的平台数不等于本转接器已经验证的平台数。 |
| 内容记录 | 有 `contentType`、文字、图片、视频、嵌入地址、总体状态；缺逐字段来源、媒体可播放性验证、稳定记录 ID 和统一错误分类。 |
| 测试 | 有模拟 OpenCLI/HTTP 的自动化测试和若干真实链接的手工验证；尚无跨平台回归样本矩阵、A2UI 输出或通用客户端契约。 |

现有代码：`src/resolver.mjs`、`src/opencli.mjs`、`src/server.mjs`、`public/app.js`。现有接口在升级期间保留，以便对照新旧输出。

## 3. 目标架构

```text
智能体 A / 智能体 B / 演示网页
              │ 链接、可选任务、客户端能力
              ▼
       通用转接 API
              │
    ┌─────────┴─────────┐
    ▼                   ▼
链接解析与内容读取       界面编排 API
    │                   ▲
    ├─ 平台 OpenCLI 命令  │ 统一记录 + 任务 + 组件目录
    ├─ Browser Bridge    │
    └─ 公开网页元信息     │
              ↓          │
       统一 ContentRecord ┘
                         ↓
                   A2UI 消息 / 普通 JSON
                         ↓
                   客户端原生组件渲染
```

**通用记录是主契约，A2UI 是可选的展示契约。** 即使某个客户端不支持 A2UI，它仍可使用统一记录渲染自己的固定卡片。平台读取器不生成 UI，界面编排层不直接操作网站。

## 4. 内容转接的实施方案

### 4.1 平台能力注册表

把当前写在 `openCliRoute()` 中的站点判断拆成注册表。每个插件声明：匹配域名与路径、支持的链接类型、OpenCLI 命令、字段映射、是否需要浏览器登录、可用媒体方式、官方播放器方式和已验证状态。通用网页读取器保底。只有通过真实链接验证的能力才标记为 `verified`。

先迁移并复测现有五个平台，再按真实需求扩展，不以 OpenCLI 平台清单直接宣称全平台兼容。新增平台要有至少一条成功链接、一条字段缺失或访问失败链接，并记录实际返回字段。短链接保留原始地址和最终地址；小红书等带签名参数的链接不得随意删参。

### 4.2 统一记录 v2

建议字段如下，详细 JSON Schema 在实施阶段编写：

```text
schemaVersion, id, kind, contentType
source: { inputUrl, canonicalUrl, platform, retrievedAt, reader }
text: { title, description, body, author }
media[]: { id, type, role, url, access: direct|official_embed|source_only|unavailable,
           state: available|unverified|blocked|expired }
retrieval: { status: complete|partial|unavailable, issues[], fieldEvidence }
extensions: { 平台特有的非通用字段 }
```

`fieldEvidence` 记录标题、正文、封面等字段来自站点命令、Browser Bridge 还是公开网页，并记录读取时间。`media.access` 区分“识别到视频”“有官方嵌入播放器”“取得直链文件”“仅能打开原站”。封面 URL 存在不等于浏览器能显示；需要单独验证或标为 `unverified`。缺失字段保持为空，不能补造正文、价格或视频地址。

`kind=product` 需要真实商品页或商品数据源提供价格、货币、购买地址及其采集时间。帖子提到某商品时仍是 `kind=content`；跨平台商品关联是另一个需要证据的模块。

### 4.3 错误与运行边界

统一返回 `login_required`、`expired_link`、`not_found`、`rate_limited`、`blocked`、`timeout`、`parse_failed`、`media_unavailable` 等机器可读原因，同时保留原链接。调用方可据此选择重试、提示登录或打开原站。保留现有 URL、DNS、重定向和大小限制，并为 Browser Bridge 增加读取权限边界：服务端不能假定所有部署环境都共享用户已登录的 Chrome；必须显式配置浏览器连接和会话归属。不要把登录 Cookie、签名参数或原始页面脚本泄露给其他调用方。

## 5. A2UI 接入方案

A2UI 官方当前将 **v0.9.1** 列为当前版本，v1.0 为候选版。实施时固定一个已被所选 renderer 支持的协议与组件目录版本，先做兼容性验证，不在同一批消息中混用版本。

新增可选接口：

| 接口 | 输入 | 输出 |
| --- | --- | --- |
| `POST /v1/resolve` | `url` | 统一记录 v2，不含界面选择。 |
| `POST /v1/compose` | `records[]`、可选 `task`、`clientCapabilities` | 经校验的 A2UI 消息；若客户端不支持，返回普通 JSON 布局建议或让客户端直接用记录。 |
| `POST /v1/resolve-and-compose` | 链接、任务、能力 | 方便演示的组合接口；内部仍调用前两层。 |

首版只用受控规则选布局，不依赖 LLM：

| 实际内容与任务 | 选择的界面 |
| --- | --- |
| 单条图文 | 封面、标题、正文、图集、来源按钮。 |
| 直链视频 | 原生视频组件、文字、来源按钮。 |
| 官方嵌入视频 | 仅当客户端明确支持且允许该平台时使用受控播放器组件；否则展示封面和原站入口。A2UI 基础 `Video` 组件不能把任意视频网页变成可播放文件。 |
| 视频不可播放或链接失效 | 可用文字/封面、明确原因、原站入口；不生成空播放器。 |
| 多条内容、探索任务 | 按内容来源或主题组织图集与内容卡。 |
| 多条内容、比较任务 | 只比较有证据的同类字段，并能回到原记录。 |

先用 A2UI 基础组件（如 `Card`、`Text`、`Image`、`Video`、`Row`、`Column`、`Button`）完成一条图文和一条直链视频的端到端演示。商品卡、图集、官方嵌入播放器如果基础目录不能准确表达，再定义有版本号的自有组件目录；不能把 iframe、任意 HTML 或 JavaScript 当作来自 Agent 的可信指令执行。客户端负责样式、链接打开动作、组件白名单和媒体播放失败状态。

后续允许智能体提出布局选择或导读，但只能引用已存在的记录 ID 和字段，并经过结构校验。**“根据内容切换界面”可先由确定性规则证明，A2UI 是输出协议，不是做决策的模型。**

## 6. 与其他智能体的复用方式

核心包不包含“逛逛、想买、预算”等购物专有逻辑。调用方通过 `task` 表达自己的目标，例如 `explore`、`compare`、`inspect`，也可以使用自由文本任务；前者用于可预测的规则，后者留给将来的智能体编排。购物智能体只是一个示例客户端，它可将帖子、商品等不同记录送入编排层。其他智能体也能只调用 `/v1/resolve`，完全不使用 A2UI。

要发布为远程共享服务时，再增加鉴权、租户隔离、限流、缓存过期策略和部署文档；当前本地 Chrome 登录态不能直接当成多用户服务的授权机制。

## 7. 开发顺序与验收

1. **统一记录**：冻结 v2 JSON Schema、字段证据和错误码；旧 `/api/resolve` 保留，新增 `/v1/resolve`。用现有五个平台的模拟样本检查映射，真实链接抽样核对字段与状态。
2. **平台插件**：迁移路由和读取逻辑；形成平台能力矩阵。逐平台验证图文、视频、短链接、登录失效和访问失败；未验证的平台只走通用回退。
3. **A2UI 最小闭环**：锁定协议与 renderer；实现 `/v1/compose`，在独立演示页显示“统一记录 / A2UI 消息 / 渲染结果”三栏。至少验证图文、直链视频、不可播放视频三种不同结果。
4. **任务驱动展示**：用同一组记录分别输入 `explore` 和 `compare`，验证产生不同布局且每项内容能追溯到原链接。再决定是否引入 LLM 辅助编排。
5. **通用接入文档**：提供 OpenAPI/JSON Schema、调用示例、浏览器登录前提、失败语义及新增平台插件说明；用一个非购物场景客户端验证复用性。

完成标准：内容记录在没有 A2UI 的客户端也可用；同一记录在不同任务下能产生可解释的不同界面；字段缺失或平台阻断时不会展示虚构内容；所有媒体入口有明确的可用状态；真实链接测试与模拟自动化测试分别报告。
